# CLAUDE.md

This is a Plotly/Dash based webpage for comparing baskets, containing financial asset, via backtesting.

## Commands

```bash
# Setup: install editable package with dev tools (from pyproject.toml)
pip install -e ".[dev]"

# Development server (hot-reload via DASH_DEBUG=true in .env)
python src/app.py
# or
gunicorn --reload src.app:server

# Production
gunicorn --config gunicorn.conf.py src.app:server

# Linting
flake8 --max-complexity=10 --max-line-length=127 ./src

# Type check (requires mypy 2.1.0 — pinned in pyproject.toml; older 1.x
# releases silently miss errors that CI's mypy 2.1.0 reports)
mypy --explicit-package-bases --ignore-missing-imports src/backtest.py src/strategies/
mypy --explicit-package-bases --ignore-missing-imports tests/test_backtest.py tests/test_strategies.py

# Tests
pytest

# Single test file
pytest tests/test_backtest.py
```

## Environment

```bash
# URL or local path to parquet files
BASE_URL=https://your-data-host/path

# set log level: CRITICAL, ERROR, WARNING, INFO, DEBUG
LOG_LEVEL=INFO

# (de-)activate dev tools of Plotly/Dash
DASH_DEBUG=false

# default reporting (base) currency pre-selected in the GUI dropdown
BASE_CURRENCY=EUR
```

`BASE_URL` must point to a directory containing `master.parquet` (asset catalogue) and one parquet file per asset (OHLCV data). The catalogue's `currency` column records each asset's quote currency, and its `currency` asset-class rows are the FX pairs (`{LOCAL}{BASE}=X`, e.g. `USDEUR=X`) used to convert prices into the reporting currency. `BASE_CURRENCY` sets only the dropdown's initial value (default `EUR`); the user picks the actual reporting currency per run.

## Dependency Management

All dependencies (runtime and development) are pinned to exact versions in `pyproject.toml` for reproducibility. The build system (`setuptools` + `setuptools-scm`) manages the package metadata, versioning from git tags, and entry points. Installation uses `pip install -e ".[dev]"` (editable install with dev tools); no separate `requirements*.txt` files exist.

**Dependency Updates**: Dependabot (GitHub Action, configured in `.github/dependabot.yml`) scans `pyproject.toml` weekly and creates pull requests with new versions. CI runs on these PRs; tests validate compatibility. Review and merge PRs to keep dependencies current.

## Architecture

**Entry point and module loading order:**
`app.py` → imports `src.callbacks` (side-effect: registers all Dash callbacks) → imports `src.layout` → `src.config` is always imported first as a module-level singleton.

**`src/config.py` — startup singleton**
Loads `.env`, configures logging, fetches `master.parquet` from `BASE_URL` into the module-level global `df` (a DataFrame). Resolves `app_version` from setuptools-scm (git tags, dev versions, or fallback); the version displays in the page footer. Exposes `base_url`, `assetsClasses`, `df`, `log`, `app_version`, and `default_base_currency` (from `BASE_CURRENCY`, default `EUR`) to the rest of the app. All other modules import this as `import src.config as _config`. Version resolution chain: (1) installed distribution metadata, (2) generated `src/_version.py` from setuptools-scm, (3) live git query, (4) fallback to `'unknown'`. For releases, tag with `git tag v<VERSION>` (e.g., `git tag v0.1.0`); setuptools-scm will then report that exact version.

**`src/backtest.py` — pure simulation engines (no Dash dependencies)**
Three strategies share this module; all parquet I/O happens here. **Every per-asset and FX-pair parquet read funnels through `_read_close_series(base_url, filename)`** — a `@functools.lru_cache(maxsize=None)` choke point that fetches each file's UTC-normalised `Close` column (only `Close` is ever consumed anywhere) from `BASE_URL` **at most once per process**, mirroring the one-shot, always-resident `master.parquet` in `config.df`. Because the cache is process-wide (not per-call), it spans separate Dash callbacks: the date-slider refresh (`_get_monthly_range()`) and the later backtest run (`load_daily_closes()`) share one read per asset, an asset in both baskets is read once, and an FX pair needed by both `load_daily_closes()` and `build_fx_columns()` is read once. The per-call `fx_cache` in `_fx_rate_series()` is retained (it also memoises the "pair missing" `None` result and avoids re-filtering the catalogue), but the underlying read is now deduplicated process-wide. The cache assumes the parquet data is static for the process lifetime (as `config.df` already does); `clear_parquet_cache()` drops it (used by the test-suite — via the autouse fixture in `tests/conftest.py` — to isolate read counts, and as a data-refresh hook). All engines run on **daily** close prices (`load_daily_closes()`), windowed to the selected months by `_window_by_month()`, and produce a daily portfolio-value curve. **Currency normalisation happens in `load_daily_closes()`** (the single choke point all strategies and order-log generators funnel through): each asset's prices are converted from its catalogue `currency` into the chosen `base_currency` by multiplying by the daily FX rate from `_fx_rate_series()` (the `{LOCAL}{BASE}=X` pair's close, ffilled/bfilled onto the asset's calendar), so a basket mixing currencies is valued consistently — the standard **unhedged** base-currency approach (no hedging). Assets already in the base currency, or with a blank/`'0'`/unknown currency (e.g. Indices), pass through unchanged; FX pairs added as basket assets take the same path via their quote currency. The base currency threads from the GUI dropdown (`bt-base-currency`) → run callback → `run_backtest()` → `strategy.run()` → `load_daily_closes()`; it defaults to the `BASE_CURRENCY` module constant for non-UI callers/tests. The catalogue may lack a `currency` column (legacy/test fixtures) — conversion is then skipped. All engines are **vectorised** (numpy array maths, no per-day Python loop) for speed: DCA cumulative-sums a (days × assets) purchase matrix; Buy & Hold and Risk-Off snapshot holdings on the (few) trade days — reusing `_rebalance_to_target()` — then value all days in one pass. The daily valuation matches `_portfolio_value()` exactly (Σ units × price over non-NaN prices, NaN-priced assets keep their units). `_portfolio_value()` and `_rebalance_to_target()` remain the per-trade primitives reused by the plugins' order-event generators. **Per-asset weighting** threads an optional `weights: dict[str, float] | None` (symbol → relative weight; `None`/empty = equal weight, fully back-compatible) through `run_backtest()` → `strategy.run()` → every engine. Two helpers centralise the rule: `_normalised_weights(symbols, weights)` (each symbol's share of an allocation, renormalised over a tradable subset — an all-zero subset → no allocation, i.e. stay in cash / skip the contribution; used by `_rebalance_to_target()` and the DCA order-event split) and `_weight_array(columns, weights)` (the vectorised all-ones-default counterpart for `simulate_dca`'s matrix, `_first_all_priced_pos()` and the all-priced gate). Weights are renormalised **per day** over whatever is priced/buyable, so a zero-weight asset gets nothing and is *not* awaited by the lump-sum "all priced" gate (`_first_all_priced_pos(prices_mat, weight_vec)` only requires the positively-weighted columns to be priced). `build_equal_weight_index()` takes the same optional `weights` (a Σ(wᵢ·rᵢ)/Σ(wᵢ) weighted daily mean; equal weights reproduce the old plain mean), so the Risk-Off signal index and the Buy & Hold benchmark column both reflect the chosen allocation.
- Buy & Hold: `run_backtest()` → `load_daily_closes()` → `_window_by_month()` → `simulate_lumpsum()` → `compute_metrics()`. `simulate_lumpsum()` deploys the whole lump sum once — split by the per-asset weights (equal by default) on the first trading day on which **every** positively-weighted basket asset is priced (`_first_all_priced_pos()`, via `_rebalance_to_target(..., inv_frac=1.0, weights)`) — then holds those units unchanged and values daily. Waiting for the whole (weighted) basket to be priced (rather than the first day *any* asset is buyable) means the initial investment follows the chosen allocation instead of over-weighting whichever listed first; if some required asset is never priced within the window the lump sum is held flat in cash.
- DCA: `run_backtest()` → `load_daily_closes()` → `_window_by_month()` → `simulate_dca()` → `compute_metrics()`. `simulate_dca()` contributes once per month — on each month's last trading day (`_is_month_end_trading_day()`) — split across that day's buyable assets by their weights; values daily.
- Risk-Off: `load_daily_closes()` (full daily history for look-back) → `build_equal_weight_index()` (weighted) → `compute_riskoff_signals()` (three booleans `_sma_trend_signal`/`_ytd_return_signal`/`_first_n_days_signal`, summed to a 0..3 positive-signal count, ÷3 = daily target fraction) → `gate_target_until_all_priced()` → `simulate_riskoff()`. Signals are evaluated daily and `simulate_riskoff()` buys/sells to the new target (via `_rebalance_to_target(..., weights)`) **only on the day the target changes**, holding (and letting the fraction drift) in between. Before the simulation the plugin runs the daily target through `gate_target_until_all_priced(price_df, target, weights)`, which forces the target to 0 (fully in cash) until the first day on which **every** positively-weighted basket asset is priced (`_first_all_priced_pos()`) — so, like Buy & Hold, the lump sum's initial deployment follows the per-asset weights rather than over-weighting whichever assets listed first. The gate is applied to the single target series both `simulate_riskoff()` and `_riskoff_order_events()` consume, keeping them in lockstep.
- `compute_metrics()` is shared by all (daily returns annualised with √252; CAGR from the calendar span; for the lump-sum path `total_invested` is the initial investment). It returns **9** metric keys (no Best/Worst Month) and rejects windows spanning fewer than three calendar months. `get_common_date_range()` finds the overlapping history across both baskets (the date slider stays month-granular).
- Order log (generic): `build_order_log(events, initial_capital)` turns a strategy's raw `OrderEvent`s into finalized `OrderRow`s (13 fixed columns — the raw trade plus derived value-after, running net deposits, P&L base-ccy/%, equity exposure, cash quota, period return — plus four per-trade dicts: `asset_values` (each asset's post-trade worth, base ccy), `asset_prices` (each asset's exchange close in the **base** currency), `asset_prices_local` (each asset's close in its own **trading** currency) and `fx_rates` (the day's rate for each `{LOCAL}{BASE}=X` pair used). The UI renders a value column per asset, **one or two** price columns per asset (the base close always; the trading-currency close too when the asset trades in a non-base currency), and one rate column per FX pair. The per-asset breakdown is produced by `_asset_values(holdings, prices)` (units × price, NaN-priced → 0, summing to `assets_after`), `_asset_prices(prices)` (the bare base-ccy close, NaN → None), `_asset_prices_local(prices, asset_rate, date)` (base close ÷ that day's FX rate = the original local close; passthrough when no rate) and `_fx_rate_values(pair_rate, date)` (the rate per pair that day) inside each plugin's events generator. The trading-currency/FX data comes from `build_fx_columns(base_url, filenames, df_meta, base_currency, index)` → an `FxColumns` namedtuple (`asset_local_ccy`, `asset_rate`, `pair_rate`), which reuses `_fx_rate_series()` and the **same** `reindex(index, method='ffill').bfill()` alignment as `load_daily_closes()`, so `base ÷ rate` exactly reconstructs the local close. The plugin threads its `FxColumns` into the events generator; with no FX context the local price degrades to the base price and no pair columns appear. This is the **only** order-log code here and is strategy-agnostic; each strategy emits its own `OrderEvent`s inside its plugin. `run_backtest()` now returns a 3-tuple `(series, metrics, order_log)`; its built-in fallback path (strategy=None, not used by the UI) runs Buy & Hold via `simulate_lumpsum()` and returns `order_log=None`.

**`src/strategies/` — strategy plugin system**
`base.py` defines the `BacktestStrategy` ABC and the `ConfigParam` dataclass (GUI-rendered, self-validating params). Besides the one-sentence `get_description()` (dropdown/tooltip summary), the ABC offers a **non-abstract** `get_long_description()` returning a richer multi-paragraph **Markdown** write-up (what it does, how it trades, when it suits, per-parameter notes); it defaults to `get_description()` so existing/3rd-party plugins keep working, and each built-in plugin overrides it. The GUI renders it as Markdown in a collapsible per-basket info panel toggled by an ⓘ icon next to the "Strategy" label. `registry.py` holds the `@register` decorator and `get_strategy()`/`list_strategies()`/`get_all_strategy_info()` (the latter's dicts now also carry `'long_description'`). Plugins are thin orchestrators over `backtest.py`: `lumpsum.py` (Buy & Hold), `dca.py` (DCA) and `riskoff.py` (Risk-Off). `__init__.py` imports every plugin module so importing the package registers all strategies; **import order is the dropdown order**, so `lumpsum` is imported first to make Buy & Hold the default GUI selection (`components._default_strategy_config()` picks `list_strategies()[0]`). Each `run()` takes a trailing `base_currency: str = 'EUR'` (forwarded to `load_daily_closes()` for FX normalisation) and `weights: dict[str, float] | None = None` (symbol → relative weight, forwarded to every engine and the events generator; `None` = equal weight), and returns `(pd.Series | None, dict | None, list[OrderRow] | None)` — the same 9 metric keys as `compute_metrics()` plus the strategy's order log. A plugin builds that log from its **own** strategy-specific events generator (`_lumpsum_order_events()` / `_dca_order_events()` / `_riskoff_order_events()`, each taking an optional `fx: FxColumns` so its events carry the trading-currency price and per-pair FX rate, **and** an optional `weights` so the per-trade split matches the simulation; they reuse the shared `_is_month_end_trading_day`/`_portfolio_value`/`_rebalance_to_target`/`_normalised_weights` primitives) fed to the generic `build_order_log()`, so adding a strategy and its order log touches only that plugin file — never `backtest.py`. Each `run()` calls `build_fx_columns()` after windowing and passes the resulting `FxColumns` into its events generator.

**`src/callbacks/`**
- `backtesting.py`: basket management, date range slider, `run_backtest` orchestration. Its run callback has **5 outputs** — chart, metrics table, status, chart style, and `bt-orders-store.data` (`{'a': rows|None, 'b': rows|None}`, each basket's display rows from `_order_rows()`); it reads the `bt-base-currency` dropdown as an extra State and forwards that reporting currency into both `run_backtest()` calls (FX conversion) and both `_order_rows()` calls (along with each basket's `_asset_currency_map(filenames, df)` so the order table can label trading-currency price columns), and labels the chart y-axis with it. Asset search dropdowns label options via `_asset_option_label(row)` (adds the asset's trading currency, e.g. `AAPL — Apple (1d · USD)`), and an added basket item stores its `currency` so `_render_basket_list` can tag it. The metrics/order values are therefore all in the selected reporting currency; a separate `render_order_table` callback renders the **active** basket's stored rows into the always-visible `bt-orders-content` div (the tabs only select; the table never lives in a `display:none` pane), and `download_orders` exports the active basket's rows as CSV / Excel via `dcc.send_data_frame` → `dcc.Download`. The daily value curve is thinned to ~2000 points by `_downsample_for_plot()` before plotting (the chart is only ~1-2k px wide; metrics use the full series) to keep the JSON payload and browser SVG render small. On strategy change the MATCH `render_strategy_params` callback now has **2 outputs** — the param inputs **and** the `{'type':'bt-strategy-desc',…}` Markdown panel (refilled via `_strategy_desc_panel()`); a separate MATCH `toggle_strategy_desc` callback flips the `bt-strategy-desc-collapse` `is_open` on each ⓘ-button click. **Per-asset weights** live in a per-basket `bt-weights-store-{a,b}` (`{filename: weight}`), kept **separate** from the basket store so editing a weight does *not* retrigger the date-range slider (which would reset the selected window). `sync_weights_a/b` (Input = the `{'type':'bt-weight-{id}','index':ALL}` values, debounced) persist edits into that store and refresh the live `{'type':'bt-weight-pct-{id}','index':ALL}` allocation-% labels **without** re-rendering the list (so the input keeps focus); `manage_basket_*` reads the weights store as a State and passes it to `_render_basket_list` so existing assets keep their weight across add/remove (a new asset is absent → default 1.0). The run callback reads both weights stores as State, translates them to symbol-keyed weights via `_symbol_weights()` (all-zero/empty → `None` = equal weight) and forwards them into each `run_backtest()` call; `reset_results_on_input_change` also listens to both weights stores so a weight edit clears stale results.
- `__init__.py` imports `backtesting` so that importing the package registers all callbacks

**UI building blocks**
- `layout.py`: top-level layout only, calls `_basket_ui()` from `components.py`; above the two basket panels it places a **base-currency dropdown** (`bt-base-currency`, options from `_base_currency_options()`, default `_config.default_base_currency`) that applies to both baskets; below the chart/metrics it places an "Orders" heading row (title left, a `dbc.DropdownMenu` download-icon button right → CSV / Excel items `bt-dl-csv`/`bt-dl-xlsx`, plus a hidden `dcc.Download`), a `dbc.Tabs` (id `bt-orders-tabs`, `tab_id` `a`/`b`) that **only selects** the active basket, a `dcc.Store` (`bt-orders-store`), and a single **always-visible** `bt-orders-content` div. The order table is **not** put inside the tab panes: a Bootstrap tab pane is `display:none` until activated and Safari won't repaint callback-injected content in the active pane until a tab switch (the table stayed blank until toggling B→A). `render_order_table` re-renders the active basket's stored rows into the always-visible div, which paints first-time like the chart/metrics.
- `components.py`: `_basket_ui` (its strategy section adds an ⓘ toggle button `{'type':'bt-strategy-desc-toggle','basket':id}` beside the "Strategy" label and a `dbc.Collapse` `{'type':'bt-strategy-desc-collapse',…}` wrapping the `{'type':'bt-strategy-desc',…}` Markdown panel built by `_strategy_desc_panel(strategy_name)` — which renders the strategy's `get_long_description()`), `_render_basket_list(basket_data, basket_id, weights=None)` (each row labelled by `_basket_item_label(item)` — `"<symbol> — <name> (<currency>)"`, the tag dropped for blank currencies — plus a per-row relative-weight `dbc.Input` `{'type':'bt-weight-{id}','index':filename}` and a live allocation-% `<span>` `{'type':'bt-weight-pct-{id}','index':filename}`, the percentages from `_weight_percentages(weight_by_key)`; `_basket_ui` adds the matching `bt-weights-store-{id}` store), `_metrics_table`, `_base_currency_options()` (the reporting-currency dropdown's choices — the distinct quote currencies from the catalogue's `currency` asset-class rows, minus blank/`'0'`/`GBp`, with the default always present), `_asset_currency_map(filenames, df)` (symbol → trading currency, fed to `_order_rows`), and the order-table pair driven by the `_ORDER_COLUMNS` spec **plus** dynamic per-asset and per-FX-pair columns: `_order_rows(orders, base_currency, asset_currency)` formats the log into JSON display rows (`{column label: text}`, the fixed `_ORDER_COLUMNS` — whose P&L header gets the `base_currency` code appended, e.g. `P&L (USD)` — followed by, per basket asset from `_order_asset_columns()`, a `<symbol> value` column and its price column(s): when the asset's `asset_currency` differs from the base currency **both** `<symbol> price (<local>)` and `<symbol> price (<base>)`, otherwise a single column (`<symbol> price (<base>)` when the currency is known, or a plain `<symbol> price` when unknown); then one `<{LOCAL}{BASE}=X>` rate column per FX pair from `_order_fx_columns()`. Stored in `bt-orders-store` and shared by the table and the CSV/Excel download. `_order_table_component(rows)` derives its column order from the row dict keys (so the per-asset and FX columns appear automatically) and renders them as a **native HTML `<table class="order-table">`** inside a single `dcc.Markdown(dangerously_allow_html=True)` (not thousands of `html.Tr`/`html.Td` — those cost *seconds* of dash-renderer per-component render; native HTML also needs no JS layout measurement, so it paints first-time inside the tabs UI), or the 'No orders.' placeholder.
- `styles.py`: shared inline style dicts. The metrics table is an `html.Table`; the order table is native HTML styled by the `.order-table` / `.order-table-wrapper` rules in `assets/layout.css` (80vh `max-height` scroll box, sticky header + sticky first column via `position: sticky`).

**Data flow**
- On startup: `master.parquet` → `config.df` (asset catalogue with symbol, name, exchange, asset_class, filename, interval)
- On user interaction: per-asset parquet files (`{BASE_URL}/{filename}`) fetched on demand; each file has OHLCV columns with a datetime index
- Basket state is held in `dcc.Store` components client-side; the backtest callback reads them as lists of `{filename, symbol, name, currency}` dicts (`currency` is the asset's trading currency, blank when unknown). Per-asset weights live in a separate per-basket `bt-weights-store-{a,b}` store (`{filename: weight}`, default 1.0 when absent)

**`@log_time` decorator** (`utils.py`) wraps every callback to emit DEBUG-level timing.
